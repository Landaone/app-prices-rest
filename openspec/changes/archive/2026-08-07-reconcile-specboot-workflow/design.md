## Context

This repo runs OpenSpec 1.7.0 with Claude and Kiro selected as clients (no Cursor, no Codex — confirmed by absence of `.cursor`/`.codex` directories). This machine's currently-generated `opsx` commands are only `propose`, `apply`, `archive`, `sync`, `update`, `explore` — but this is a **machine-global `custom` profile selection**, not a limitation of the OpenSpec 1.7 CLI itself. `openspec config list` (read-only) confirms: `profile: custom (explicit)`, `workflows: propose, explore, apply, update, sync, archive (explicit)`, stored in `~/.config/openspec/config.json` — a machine-wide file, not `openspec/config.yaml` (which has no `profile`/`workflows` keys at all; confirmed by `grep`, no match). The installed package's own `dist/core/templates/workflows/verify-change.js` proves the CLI **does** ship an official `verify` workflow (both a skill template and an `/opsx:verify` command template); `dist/core/profiles.js`/`.d.ts` confirms `ALL_WORKFLOWS` includes `verify`, `new`, `continue`, `ff`, `bulk-archive`, `onboard`, and that a `custom` profile can enable any subset of them independently — a different developer's machine, or this one after a global config change, may have `/opsx:verify` available. `ai-specs/specboot-instructions.md` and its own template copy at `packages/specboot/template/ai-specs/specboot-instructions.md` each independently document a workflow that includes commands (`/new`, `/ff`) from an older OpenSpec generation, drifted from each other and from what is installed — that part of the gap is real regardless of the verify-availability correction above.

The reference adoption in `AI4Devs-LTI-extended` ran OpenSpec 1.3.1, which generated a `verify` command and an `openspec-verify-change` skill (3-dimension report: Completeness/Correctness/Coherence; CRITICAL/WARNING/SUGGESTION severities; graceful degradation when fewer artifacts exist). Reading the **currently installed 1.7 package's** `verify-change.js` directly shows this template is byte-identical to that 1.3.1 content — OpenSpec has not updated it. Read-only testing in this repo (`openspec instructions apply --change "reconcile-specboot-workflow" --json`, exit 0) confirms its `contextFiles` map **does** work correctly against this repo's 1.7 install — an earlier draft of this document incorrectly suggested this I/O assumption "needs re-validation" and might not hold; it holds. The reason to still avoid the official template is not that it's broken — it is that its own shipped conclusion ("Ready for archive" after only Completeness/Correctness/Coherence, no adversarial-review or human-approval concept, CRITICAL/WARNING/SUGGESTION taxonomy) is incompatible with this repo's mandatory sequence and cannot be edited once the file becomes OpenSpec-generated. See "Official verify vs. custom SpecBoot verify" below and proposal.md for the motivating gap.

This repo already has a working `adversarial-review` skill (canonical, symlinked into both clients) with a severity model and PASS/PASS WITH GAPS/FAIL verdict — it just lacks reviewer-provenance reporting and isn't formally wired into a mandatory sequence with a verify step.

**Namespace constraint discovered on review**: `.claude/commands/opsx/` and `.kiro/prompts/` today contain *only* files generated by the OpenSpec CLI (confirmed: all 6 files in each match the `opsx`/`opsx-` generated set, with zero precedent for a hand-added file coexisting there — unlike `.claude/skills/` and `.kiro/skills/`, which already mix 6 generated `openspec-*` directories with 11 hand-added `ai-specs` symlinks). Placing a new verify command inside the `opsx` namespace would be the first hand-added file in an otherwise fully-generated directory, and the installed CLI's own behavior (see below) is not documented in enough detail to rule out that directory being treated as fully owned by OpenSpec during a future `openspec init`/`openspec update`.

**Read-only regeneration-safety evidence gathered** (no install/download/upgrade performed):
- `openspec --help`: `init` "Initialize OpenSpec in your project" (has a `--force` flag described as "Auto-cleanup legacy files without prompting" — implying some notion of files it recognizes as its own "legacy" output); `update` "Update OpenSpec instruction files".
- `openspec init --help` / `openspec update --help`: no flag or description claims scanning for, or deleting, arbitrary unrecognized files in a generated directory.
- The installed package's own `README.md` (`@fission-ai/openspec`, via `npm root -g`) describes `openspec update` as: "Run this inside each project to regenerate AI guidance and ensure the latest slash commands are active" — i.e., it regenerates the commands/skills *it* generated, not documented as touching arbitrary directory contents.
- `openspec doctor --json` in this repo returns `{"root": {"healthy": true, "status": []}, ...}` — it does not flag, enumerate, or warn about the 11 existing hand-added `ai-specs` skill symlinks already living inside `.claude/skills/`/`.kiro/skills/`, which is the closest existing precedent for a mixed generated/hand-added directory in this repo.

This evidence is suggestive, not a guarantee — it is the extent of what can be checked without installing, downloading, or reading OpenSpec's private implementation. The design proceeds on it but records the residual risk explicitly (see Risks).

**Group 11 context: the enriched-artifact handoff gap.** The independent adversarial review that blocked archive found `packages/specboot/bin/init.js:88` still printing `/enrich-us  ->  /ff  ->  /apply` — a retired-command defect Group 10's sweep missed because it only grepped Markdown/doc content, not the JS installer. Fixing that one line exposed that this change had never formally specified `enrich-us` itself: what it consumes, what it must produce, or how its output reaches `opsx:propose`. The confirmed historical workflow in `AI4Devs-LTI-extended` was `enrich-us -> enriched Markdown artifact -> opsx:new -> opsx:ff -> opsx:apply` — evidence: historical commit `3bcc6d1` explicitly added saving the enriched user story and moving it through `opsx:new`; the historical canonical `enrich-us` skill produced a Markdown artifact as its output; historical `opsx:new` and `opsx:ff` ingested attached artifacts as their input; and changes archived under that history retain files such as `improved-user-story.md` and `scrum-80-enhanced.md` alongside the change they informed — durable proof the artifact was treated as the change's authoritative input, not a throwaway chat message. In OpenSpec 1.7, `opsx:propose` replaces the combined `new + ff` sequence (already established by this change's Goals), but no prior group re-established what `new + ff` used to receive as input. `enrich-us` is confirmed as this team's pre-proposal refiner: it takes a work item, finds omissions/ambiguities, adds repository-specific technical detail, and must produce an implementation-ready Markdown artifact that OpenSpec proposal generation consumes as its authoritative input.

**Group 11 context: Phase-1 integration boundary.** The current implementation must be self-contained and must not require Jira or any external ticket system. Supported inputs are work-item text pasted into the conversation, a screenshot attached to the conversation, or a readable attached document/text artifact; if the client cannot reliably extract the input, it must ask for the missing text/clarification rather than invent content. Jira MCP, automatic ticket retrieval, Jira write-back, and ticket-status transitions are a separately approved future phase, not configured, implemented, validated, or required here. Historical Jira behavior (the pre-existing `enrich-us` skill's step 1/6/7, and `ai-specs/specboot-instructions.md`'s "Optional: MCP Integrations (Jira + Playwright)" section) may be cited as evidence of the historical shape, but current guidance must not imply Jira is available or required — the pre-existing skill text modeled Jira as the *default* input source ("Use Jira MCP to get the ticket details... whether it is the ticket id/number...") which is corrected here to direct-input-first.

**Group 11 context: `opsx:propose`'s actual input contract (evidence for the handoff-mechanism decision).** Reading `.claude/commands/opsx/propose.md` and `.kiro/prompts/opsx-propose.prompt.md` directly (both files this change is forbidden from modifying) confirms their **only** documented input channel: "The argument after `/opsx:propose` is the change name (kebab-case), OR a description of what the user wants to build" — a conversational argument/description, not a file path or attachment reference. There is no `--file`/`--input` flag, no read of a well-known staging path, and no mechanism to inject an external artifact other than what the invoking session says or pastes. This is decisive evidence for the handoff-mechanism decision below: any mechanism that assumes `opsx:propose` will read a file on its own is false, and any mechanism that requires editing `propose.md`/`opsx-propose.prompt.md` to add file-ingestion is forbidden by this change's own scope boundary.

**Group 12 context: the staging-ignore portability gap.** Group 11 verified, in *this* repository, that `.specboot/staging/` is correctly ignored — but only by editing this repository's own root `.gitignore` directly. Two facts, checked directly for this correction, show that verification does not generalize to an adopting project: (1) `find packages/specboot/template -iname ".gitignore"` returns nothing — the distributed template ships no `.gitignore` at all, so a fresh `openspec init`-style adoption via `npx @lidr/lidr-specboot` provisions no ignore rule anywhere; (2) `packages/specboot/bin/init.js`'s `copyRecursive` (see `Instructions` section of that file) skips any destination path that already exists (`pathExists(destPath)` → push to `stats.skipped`) rather than merging — so even if the template *did* ship a `.gitignore`, an adopting project with its own pre-existing `.gitignore` would never receive the merged rule; the file would simply be skipped whole. The combination means: a fresh adoption into a repo with no prior `.gitignore` gets nothing (no template `.gitignore` exists to copy); a fresh adoption into a repo with an existing `.gitignore` also gets nothing (skipped). Either way, `.specboot/staging/` is unignored by default for every adopting project, and `enrich-us`'s own instructions (Group 11) unconditionally write to it — the two facts combine into the concrete defect: `enrich-us` can silently write an untracked, unignored work-item draft into a project that never asked for one.

**Group 13 context: the installer-versus-configured-capability gap.** The latest independent adversarial review returned FAIL with one Major and one Minor. Major: `packages/specboot/bin/init.js`'s client-provisioning loop is, and always has been, `for (const tool of ['.claude', '.cursor'])` (confirmed by direct re-read) — it has never provisioned Kiro. Yet `README.md`, `ai-specs/specboot-instructions.md`, and the template copy present Kiro command syntax (`/opsx-propose`, `/opsx-apply`, `/opsx-archive`, the "Kiro syntax" example block) throughout the workflow section with no disclosure that the installer does not create it. This repository has a valid, working `.kiro/` setup (`.kiro/prompts/*.prompt.md`, `.kiro/skills/*`, `.kiro/settings/*`) — but it exists because it was configured separately (by hand or by a separate adoption step), not because `npx @lidr/lidr-specboot` created it. A reader following only this document's Kiro examples after running the installer would hit missing capabilities with no warning that this was expected. Minor: `ai-specs/skills/specboot-verify/SKILL.md` Step 5 checks capability *availability* (do the paths exist and resolve on disk right now) but its wording didn't distinguish that from provisioning *provenance* (which installer, person, or process created those paths) — a PASS on this repository's own Kiro paths could be misread as "the installer creates Kiro support," which is false.

**Group 13 context: why not just add `.kiro` to the installer loop.** Unconditionally adding `.kiro` to `packages/specboot/bin/init.js`'s `for (const tool of ['.claude', '.cursor'])` loop was considered and rejected as out of scope for a documentation/provenance correction: it would create adapters for a client this change has no evidence is "selected" by every adopting project (the installer has no client-selection mechanism at all — it unconditionally provisions whatever is in that array for every install), contradicting the selected-client-only policy this change has held to throughout (see `SPECBOOT_ADOPTION_GUIDE.md` §2's "No resources are added for unselected clients" and this document's own repeated "no adapter for an unselected client" rule). A correct fix needs explicit client selection first, not a third hard-coded entry in an unconditional loop — see "Future candidate change" below.

**Group 15 context: the broken no-op promise.** Group 12's own `proposal.md` bullet promised: "if the rule (or an equivalent broader `.specboot/` rule) is already present, make no change." The implemented `ensureGitignoreStagingRule()` (Group 12) only ever checked `content.split(/\r?\n/).some(line => line.trim() === STAGING_RULE)` — an exact-line match. A target `.gitignore` containing a broader rule such as a bare `.specboot/` line (which, under normal Git semantics with no negation, already causes every path under `.specboot/`, including `.specboot/staging/`, to be ignored) would not match that exact-line check, so the function would still append the narrow `STAGING_BLOCK` — technically harmless (still no broadening, still no removed/reordered content, staging still ends up ignored either way) but not the byte-for-byte no-op the proposal explicitly promised, and a real behavioral gap between documented and implemented behavior. An independent adversarial review correctly flagged this as a Major defect: an artifact/implementation divergence, not merely a wording issue.

**Group 16 context: the unresolved-question gap in the verdict mapping.** `ai-specs/skills/adversarial-review/SKILL.md`'s Step 5 (as it stood after Group 10) stated the mapping as: (1) Blocker or Major present → FAIL; (2) else, Minor count > 0 → PASS WITH GAPS; (3) else → PASS. Re-read literally against a Findings table containing only `Question / assumption` rows (zero Blocker, zero Major, zero Minor): rule 1 doesn't apply, rule 2's specific "Minor count > 0" test is false, so the mechanical reader falls through to rule 3's "no findings of any severity → PASS" — even though the table is not actually empty; it still contains open questions genuinely awaiting human or author confirmation. This is precisely the class of defect this change's own Group 10 correction was created to close for a different case (an open Major self-reporting `PASS WITH GAPS`) — the same "verdict prose present but not structurally exhaustive" failure mode recurring in a new corner of the same mapping. The fix must not invent a fourth severity (the request is explicit: `Question / assumption` "remains a finding category requiring confirmation, not a fourth severity") — it must instead make the existing three-severity mapping *exhaustive* over all rows actually present in the table, whatever their category.

## Goals / Non-Goals

**Goals:**
- Restore a pre-archive verification capability equivalent in spirit to the historical `verify` step, adapted to the 1.7 CLI's actual command/instruction shape.
- Make the corrected mandatory sequence (apply → SpecBoot verify → adversarial-review → human approval → archive-with-built-in-sync → post-archive strict validation) explicit and documented, as two **separate, sequential** gates: SpecBoot verify PASS/PASS WITH GAPS only makes a change **eligible for independent adversarial review** — it never by itself permits archive approval. Archive approval requires adversarial review to *also* reach PASS/PASS WITH GAPS, plus explicit human approval. Both gates are documented process gates (see Decisions), not technical restrictions on the archive command.
- Use a SpecBoot-owned namespace/name for the verify capability — distinct from any name or namespace OpenSpec's CLI generates or documents for Claude (`opsx` command directory) or Kiro (`opsx-` prompt prefix) — so it cannot collide with, or be mistaken for, OpenSpec-owned content, and standardize on a single invocation string (`/specboot-verify`) across both selected clients.
- Keep the canonical skill client-neutral and add only the adapters each client actually needs — no adapter file whose only content is "delegate to the skill" when the skill's own client-side registration already provides a working, directly-invokable entry point.
- Remain the authoritative SpecBoot verification gate regardless of whether an official `/opsx:verify` happens to be enabled on a given machine; document coexistence rather than assuming either permanent absence or a conflict.
- Encode the shell-execution lessons (exit-status preservation, no `npx --yes`, no assumed shell portability, no inferred PASS, expected-diff handling) as skill rules so future verification runs can't silently regress on them.
- Reconcile every live, present-tense reference to retired workflow names found across this repository's root/doc documentation (not only `ai-specs/specboot-instructions.md`), editing canonical symlink targets rather than their aliases, while leaving clearly-labeled historical records untouched.
- Make `adversarial-review`'s Blocker/Major/Minor verdict mapping an explicit, checkable rule (spec requirement plus matching skill procedure/output format), not just descriptive prose.
- Validate adapter placement safety using only documented/read-only checks — no assumption of undocumented CLI internals.
- Make `enrich-us` a mandatory, self-contained (Jira-free Phase 1) pre-proposal refinement gate that produces a concrete enriched Markdown artifact and an explicit `READY FOR PROPOSAL`/`NEEDS CLARIFICATION` outcome, and restore a portable handoff of that artifact into `opsx:propose` without modifying or duplicating OpenSpec's own proposal-generation logic.
- Extend the required-workflow-capability matrix from five to six capabilities (`enrich-us` first), for both selected clients.
- Correct `packages/specboot/bin/init.js`'s printed workflow guidance to be portable and client-neutral, and correct every other live reference to the retired `enrich-us -> ff -> apply` sequence repository-wide (not Markdown-only).
- Make `.specboot/staging/` provisioning portable to every adopting project: `packages/specboot/bin/init.js` SHALL idempotently ensure the target repository's `.gitignore` contains the exact narrow rule, whether or not one already exists, without ever broadening the rule or disturbing unrelated content. `enrich-us` SHALL verify the path is actually ignored before writing to it and SHALL fail safely (report, don't silently write) when it is not.
- Make documentation distinguish current repository capability *availability* from installer *provisioning*: a capability's paths existing and resolving in this repository's filesystem SHALL NOT be documented or verified as proof that the SpecBoot npm installer created them. Kiro invocation guidance SHALL be qualified as applying only where Kiro has been separately configured. Distributed templates SHALL accurately disclose which clients the shipped installer actually provisions.
- Make the staging-ignore no-op guarantee true in practice, not just in prose: `packages/specboot/bin/init.js` SHALL recognize any existing rule that already causes Git to treat a probe path under `.specboot/staging/` as ignored — not only the exact narrow line — as satisfying the requirement, when Git's own evaluation is available; it SHALL fall back to the previous exact-line check only when Git evaluation cannot be run.
- Make `adversarial-review`'s verdict mapping exhaustive over every finding category that can appear in its Findings table (Blocker, Major, Minor, and unresolved `Question / assumption`) without introducing a fourth severity: any table containing so much as one unresolved `Question / assumption` and nothing higher-severity SHALL map to PASS WITH GAPS, exactly as a Minor-only table does; only a table with genuinely nothing outstanding SHALL map to PASS.

**Non-Goals:**
- Restoring `/opsx:new`, `/opsx:ff`, `/opsx:continue`, `/opsx:bulk-archive`, or `/opsx:onboard` — these are superseded by `/opsx:propose` and `/opsx:update` in 1.7, or out of scope entirely.
- Configuring Cursor or Codex clients, or any model-routing policy.
- Restructuring the permission model — only cross-referencing the already-verified approach in `SPECBOOT_ADOPTION_GUIDE.md`.
- Commit/push/PR gate hardening.
- Modifying the installed, OpenSpec-generated `/opsx:archive` or `/opsx:sync` commands to add a technical enforcement gate — the severity gate is process-level only (see Decisions).
- Requiring a separate `/opsx:sync` invocation immediately before an archive that already performs sync internally.
- Enabling the official `/opsx:verify` workflow, or making any other change to the machine-global OpenSpec profile/workflow configuration (`~/.config/openspec/config.json`) or running `openspec update` — no step in this change mutates machine-global OpenSpec settings, silently or otherwise.
- Configuring, implementing, validating, or requiring Jira MCP, automatic ticket retrieval, Jira write-back, or ticket-status transitions — these remain a separately approved future phase; this change only ensures current guidance does not imply Jira is available or required.
- Modifying `.claude/commands/opsx/propose.md` or `.kiro/prompts/opsx-propose.prompt.md` to add file-ingestion or any other new input channel — the handoff mechanism works within their existing, unmodified conversational-description input contract.
- Redesigning `packages/specboot/bin/init.js`'s client-selection logic, its `copyRecursive`/`createSymlink` mechanism for anything other than `.gitignore`, or any other part of the installer beyond the narrow `.gitignore`-provisioning addition (Group 12).
- Adding Kiro provisioning to `packages/specboot/bin/init.js` in this change, in any form — including adding `.kiro` to the existing `for (const tool of ['.claude', '.cursor'])` loop. A selected-client-aware installer redesign (explicit client selection, conditional adapter creation per client, Windows portability, idempotent upgrades/migration) is an explicit future non-goal of this change — see the "Future candidate change" decision below. This change only corrects documentation and verifier wording to accurately reflect the installer's current, unchanged behavior.
- Introducing a fourth severity level, or any alternative taxonomy, to `adversarial-review`. `Question / assumption` remains a finding *category* that requires confirmation, distinct from and orthogonal to the three severities (Blocker/Major/Minor) — the Group 16 fix corrects how that category is *mapped* to the existing three-way verdict, not what it *is*.

## Decisions

**Adapt, don't copy, `openspec-verify-change`.** The historical skill's three-dimension report (Completeness/Correctness/Coherence) is a reusable concept, but its literal CLI calls target 1.3.1's `instructions apply --json` shape, and its severity taxonomy (CRITICAL/WARNING/SUGGESTION) is replaced rather than reused (see below). The new `ai-specs/skills/specboot-verify/SKILL.md` keeps the three-dimension report structure, but calls only `openspec status --change <name> --json` and reads the artifact files it names directly — it does **not** call `openspec instructions <artifact> --change <name> --json`; an earlier draft of this document incorrectly claimed it did, and that claim has been removed rather than adding an unnecessary command to match it. The skill adds the Blocker/Major/Minor severity taxonomy and next-gate rule, reviewer-provenance requirement, execution-provenance requirement, shell-execution rules, and per-client capability-availability check that the 1.3.1 version never had.
- Alternative considered: restore the exact 1.3.1 skill (or equivalently, enable the official 1.7 template, which is byte-identical to it) unmodified. Rejected — not because its CLI calls are broken against 1.7 (read-only testing confirmed `openspec instructions apply --json` works correctly here), but because its severity taxonomy and "ready for archive" conclusion are incompatible with this repo's mandatory sequence and, once OpenSpec-generated, could never be edited to fix that. See "Official verify vs. custom SpecBoot verify" below.

**SpecBoot-owned name, standardized as `/specboot-verify` for both clients — Claude via skill symlink, not a separate command adapter.** Kiro's adapter is `.kiro/prompts/specboot-verify.prompt.md`, a flat file using the `specboot-` prefix instead of OpenSpec's own `opsx-` prefix — invoked as `/specboot-verify`, per the naming convention confirmed across all 6 existing Kiro prompts (see Context). Claude is exposed solely through the skill symlink `.claude/skills/specboot-verify` → `../../ai-specs/skills/specboot-verify`, discovered directly from the skill's own `name: specboot-verify` frontmatter — also `/specboot-verify`, an identical string to Kiro's.
- Alternative considered (originally implemented, then reverted): an additional thin command adapter at `.claude/commands/specboot/verify.md` in a dedicated `commands/specboot/` directory, invoked as `/specboot:verify` (Claude Code maps `commands/<dir>/<file>.md` → `/<dir>:<file>`, the same mapping observed for `commands/opsx/propose.md` → `/opsx:propose`). Reverted after the first independent verification run's own evidence (see Context) showed the skill symlink alone is discoverable and is what a fresh session actually invokes — the command file registered as a second, differently-named entry point (`specboot:verify` vs `specboot-verify`) to the same capability, which was never exercised in practice and only added a documentation-accuracy risk (this change's own docs briefly stated the wrong invocation for Claude as a direct result). The file and its now-empty parent directory were removed; nothing under `commands/opsx/` was touched by the removal.
- Alternative considered: place a new command inside `commands/opsx/` / name the prompt `opsx-verify.prompt.md`, matching the historical AI4Devs command name. Rejected on review — those locations today contain *only* OpenSpec-generated files with no existing precedent for hand-added content, unlike the `skills/` directories, and the CLI's regeneration behavior for its own namespace is not documented precisely enough to guarantee a same-namespace hand-added file survives every future `openspec update`.

**Client-neutral skill, minimal per-client adapters.** Canonical logic lives once in `ai-specs/skills/specboot-verify/`. Kiro needs its own prompt file (`.kiro/prompts/specboot-verify.prompt.md`) because Kiro's prompt and skill registration are apparently separate surfaces there too, and removing it was not evidenced as safe the way the Claude command adapter was; Claude needs no separate adapter file at all, because its skill symlink (`.claude/skills/specboot-verify`) is independently sufficient. Selected-client skill symlinks (`.claude/skills/specboot-verify`, `.kiro/skills/specboot-verify`) follow the same pattern already used for the 11 existing `ai-specs/skills/*` entries symlinked into both clients.
- Alternative considered: write the full verification logic directly into each client's command/prompt file. Rejected — duplicates logic across clients and reintroduces the drift this change exists to fix.

**Official verify vs. custom SpecBoot verify — retain the custom skill, do not enable or wrap the official workflow.** Comparing the installed 1.7 package's official `verify-change.js` template against every requirement of `ai-specs/skills/specboot-verify/SKILL.md`: both cover Completeness/Correctness/Coherence equivalently; the official template has **no** equivalent of the shell-execution-integrity rules, the Blocker/Major/Minor severity gate, the next-gate policy (verify → adversarial-review eligibility, never archive approval), the mandatory execution-provenance section, the per-client capability-availability check, or the adapter-placement-safety check — all six are SpecBoot-specific and absent from the official template, which instead concludes "Ready for archive" directly. Three options were compared:
- **A — enable official `/opsx:verify`** (via the machine-global `workflows:` list). Rejected: its own shipped conclusion bypasses the mandatory sequence, and once enabled it becomes an OpenSpec-generated file this change's own rules forbid editing — so the incompatibility could never be patched, only worked around. Also out of reach mechanically here: it requires a machine-global config edit and `openspec update`, both explicitly out of scope.
- **C — layer SpecBoot policy around the official verifier.** Rejected: since the official skill/command would be OpenSpec-generated once enabled, a wrapper could not edit its taxonomy or "ready for archive" conclusion — it would have to fully re-derive/override the official report, meaning two overlapping implementations to keep in sync forever, for no capability gain over option B.
- **B — retain `/specboot-verify` as the sole, policy-enhanced SpecBoot verifier** (chosen). This is the only option with exactly one verification surface, one severity vocabulary, and one gate wording. **Idempotent, non-destructive `.gitignore` staging-rule provisioning, plus a matching runtime guard in `enrich-us` itself.** Two complementary mechanisms, not one:

**Ignore detection prefers Git's own evaluation over a custom parser, with the prior exact-line check retained as fallback.** `ensureGitignoreStagingRule()` now first attempts `git -C <target> check-ignore --quiet <probe>`, where `<probe>` is a literal, forward-slash path under the staging directory (`.specboot/staging/.specboot-probe`) that does not need to exist on disk — `git check-ignore` evaluates ignore rules against a pathname, not a real file (verified empirically: the check succeeds identically whether or not the probe file is actually present). Git's exit code is authoritative and interpreted narrowly:
- **Exit `0`** — some rule (the exact narrow line, a broader `.specboot/` rule, or anything else) already causes Git to ignore the probe. Treated as **definitively ignored**: `.gitignore` is left completely untouched, a true byte-for-byte no-op.
- **Exit `1`** — Git cleanly determined no rule ignores the probe. Treated as **definitively not ignored**: the installer appends the narrow `STAGING_BLOCK`, using the exact same create/append logic as before (create if absent, append with newline/blank-line handling if present) — behaviorally unchanged from Group 12 in *what* gets written, only *when* it decides to write has improved.
- **Anything else** (git binary missing/`ENOENT`, the target is not inside a Git repository, or any other non-`0`/`1` exit status) — Git's evaluation is **unusable**, not merely "reporting not-ignored." Falls back to the pre-Group-15 conservative behavior: read `.gitignore` if it exists, check for the exact trimmed `.specboot/staging/` line, and only append if that exact line is absent (a repository with a broader-but-unrecognized rule in this fallback path may receive a redundant, harmless narrow line appended below it — an accepted, documented limitation of the no-Git fallback, not a new defect, since the fallback's contract (per requirement 4 in this change's own request) is exact-line recognition only, not semantic evaluation).
- Alternative considered: write a custom `.gitignore` pattern matcher (handling `.specboot/` prefix matches, trailing-slash directory semantics, negation with `!`, etc.) to decide "already covered" without invoking Git. Rejected — explicitly out of scope per this correction's own instruction ("Do not implement a simplistic custom `.gitignore` parser"), and for good reason: `.gitignore` pattern semantics (anchoring, `**`, character classes, negation precedence based on line order) are intricate enough that a hand-rolled matcher would be a second, drifting reimplementation of logic Git already gets right — exactly the kind of duplicated-logic risk this change has avoided everywhere else (e.g. the enriched-artifact handoff decision explicitly rejecting reimplementing `opsx:propose`'s own logic).
- Alternative considered: always require Git and treat its absence/failure as an installer error. Rejected — the installer has no other Git dependency today, and requiring Git for a repository that might be freshly initialized or intentionally Git-less (e.g. `npx @lidr/lidr-specboot` run before `git init`) would be a new, stricter precondition than any other part of the installer enforces; the conservative fallback already existed for exactly this class of environment and continues to be sufficient (if imperfect for the broader-rule case) rather than blocking the install entirely.
- Alternative considered: use `git status --ignored` or read `.git/info/exclude` plus global excludes manually and combine with `.gitignore` parsing by hand. Rejected — `git check-ignore` is the single command purpose-built for exactly this question ("is this path ignored, considering every applicable source"), already covers `.git/info/exclude` and any configured global excludes in addition to `.gitignore`, and needs no combination logic of our own.

**Verified Git behavior for the negation edge case — tested directly, not assumed.** Two negation constructions were tested against a real, initialized Git repository with `git check-ignore -v` before writing any spec/design text about the outcome, because the first draft of this reasoning turned out to be wrong when actually tested:
- **`.specboot/` (directory-match, trailing slash) followed by `!.specboot/staging/`** — `git check-ignore -v` reports the probe **still ignored** (exit `0`, matched by the `.specboot/` line, not the negation). This is Git's documented behavior: "it is not possible to re-include a file if a parent directory of that file is excluded" — a directory-trailing-slash pattern excludes the directory itself, and Git does not descend into an excluded directory to evaluate a negation for a path inside it, so the `!` line is silently ineffective. In this case the installer correctly treats the probe as ignored (`gitVerdict === true`) and makes no change — a byte-for-byte no-op, exactly as for any other already-covered broader rule, since the path genuinely remains ignored regardless of the negation's presence.
- **`.specboot/*` (single-level glob, no trailing-slash directory exclusion) followed by `!.specboot/staging/`** — `git check-ignore -v` reports the probe **not ignored** (exit `1`); this negation *does* take effect, because `.specboot/*` does not exclude the `.specboot` directory itself for descent purposes the way a trailing-slash or `**` pattern does, so Git can still evaluate the negation for the immediate `staging` entry. In this case the installer correctly appends the narrow `.specboot/staging/` rule (verified: appended after the negation, it becomes the new last-matching rule for that path, and a follow-up `git check-ignore` after the append confirms the probe is ignored again — the negation is resolved by the append, not defeated by it).
- The initial draft of this paragraph incorrectly assumed any `!`-negation following a broader `.specboot/`-style rule would successfully un-ignore the staging path. Testing showed this depends entirely on the exact pattern syntax used for the broader rule (`.specboot/` and `.specboot/**` both block the negation; `.specboot/*` does not) — a further demonstration of why this correction defers to Git's own evaluation (Decision above) rather than attempting to hand-roll pattern-precedence logic: even reasoning about two lines of `.gitignore` by hand produced a wrong answer on first attempt.

**Verdict mapping made exhaustive by category, not by adding a fourth severity.** The corrected Step 5 procedure in `ai-specs/skills/adversarial-review/SKILL.md` now has two phases, applied in order immediately before writing the verdict:
1. **Resolve every `Question / assumption` row first.** For each such row still in the Findings table, decide — using only what was actually investigated during this read-only review — whether it was resolved with recorded evidence (an answer found in the spec/code/tests/PR, or an explicit confirmation already on record) or remains genuinely open. A row may be removed from the table **only** in the resolved case, and only together with a recorded note of the evidence that resolved it (in the Findings table itself, marked resolved with its evidence, or in the surrounding narrative — but never silently dropped with no trace). A row with no such evidence stays in the table as an open, unresolved finding — it is never removed merely because the reviewer judged it "probably fine" or "likely not material."
2. **Count what remains, then apply the exhaustive mapping:**
   - Blocker count + Major count > 0 → **FAIL** (unchanged from Group 10).
   - Else, Minor count > 0 **or** unresolved `Question / assumption` count > 0 → **PASS WITH GAPS** (widened from Group 10's Minor-only test).
   - Else (the table has nothing left in it, of any category) → **PASS**.
- Alternative considered: add a fourth severity (e.g. treat `Question / assumption` as its own tier between Minor and Major). Rejected — explicitly excluded by this correction's own instructions, and unnecessary: the actual defect was never that `Question / assumption` needed its own severity-based consequence distinct from Minor's, only that the mapping's rules didn't mention it at all. Folding it into the same PASS WITH GAPS branch as Minor (both mean "not blocking, but not nothing either") is the smaller, sufficient fix.
- Alternative considered: require every `Question / assumption` to be resolved before a verdict can be recorded at all (i.e., treat an unresolved question like a Blocker). Rejected — this would make `adversarial-review` unable to ever conclude a review that surfaces a genuine, unresolvable-without-a-human question, which contradicts the category's own defined purpose ("needs human or author confirmation" — i.e., it is expected to sometimes leave the review at PASS WITH GAPS pending that confirmation, not to block the review from concluding at all).
- Alternative considered: silently drop unresolved `Question / assumption` rows from the final table so they don't affect the count (treating them as advisory-only, never gating). Rejected — explicitly forbidden by this correction's requirements ("must not be silently treated as resolved or omitted"), and would defeat the category's purpose: a question a reviewer couldn't answer is exactly the kind of thing a human approving archive should see, not a detail quietly discarded from the report.

## Risks / Trade-offs

- [The adapted verify skill's data-gathering assumptions could still drift from a future OpenSpec release] → Mitigate by having the skill itself assert on the actual `status` JSON shape it receives and fail loudly (not silently degrade) if expected fields are absent, rather than assuming today's 1.7 shape is permanent.
- [Two skills (`specboot-verify` and `adversarial-review`) now jointly gate archive approval] → Mitigate by keeping the mandatory-sequence documentation in one place (`ai-specs/specboot-instructions.md`) so the ordering and pass/fail contract between them isn't duplicated or allowed to diverge.
- [Reviewer-provenance fallback (same-session subagent) is weaker than true cross-session review] → Mitigate by requiring the fallback to be explicitly named in the output, so a reader can judge the strength of the review rather than assuming independence that wasn't achieved.
- [Adapter-placement-safety evidence is read-only and current-version-only; a future OpenSpec release could change what `openspec update`/`init` treats as its own surface] → Mitigate by keeping the SpecBoot adapter's naming and directory distinct from any currently documented OpenSpec-owned pattern, and by re-running the same read-only checks (`openspec --help`, `openspec doctor`) as a standing task whenever OpenSpec is upgraded, rather than treating today's evidence as a one-time, permanent guarantee.
- [The Blocker/Major gate is only as strong as human/agent discipline, since `/opsx:archive` does not technically enforce it] → Mitigate by stating this limitation explicitly in `ai-specs/specboot-instructions.md` and in the SpecBoot verify skill's own output, so it is never presented or relied upon as a technical safeguard.
- [A developer whose machine has the official `/opsx:verify` enabled could invoke it instead of `/specboot-verify`, getting the "ready for archive" conclusion with none of this repo's gates applied] → Mitigate by documenting the coexistence policy explicitly in `ai-specs/specboot-instructions.md`: `/specboot-verify` is authoritative regardless of `/opsx:verify`'s presence; presence alone is not a failure (no namespace collision), but the workflow must direct users to `/specboot-verify`.
- [A client's own skill-vs-command resolution/precedence, when both a skill and a same-purpose command exist, is not fully knowable without live testing on that client] → Mitigate by relying on the simpler, single-registration design (skill symlink only, for Claude) rather than assuming two registrations resolve predictably or consistently.
- [Other live, present-tense references to retired workflow names could still exist outside the specific locations checked in this correction] → Mitigate by having explicitly enumerated and independently inspected every location named for this correction before editing, and by distinguishing historical (already-labeled) records from live instructions rather than assuming any single grep pass is exhaustive across the whole repository.
- [Making `adversarial-review`'s verdict mapping deterministic in the spec/skill text does not, by itself, guarantee a future session applies it correctly] → Mitigate the same way `specboot-verify`'s own gate is mitigated: an explicit, checkable rule in both the spec and the skill's own output format narrows the room for a session to informally deviate, even though — like every other gate in this change — final enforcement still depends on the session actually following its own documented procedure.
- [`.specboot/staging/` is a new, hand-authored gitignore rule rather than a pre-existing, verified-ignored path — an incorrect or overly broad rule could either leak staged work-item drafts into commits or silently swallow unrelated files] → Mitigate by verifying, before adding the rule, that no existing `.gitignore` entry already covers or conflicts with it, and after adding it, that `git check-ignore` confirms exactly the intended path is ignored and nothing broader.
- [The copy-staged-file-into-the-change-directory traceability step is documented, manual guidance, not a technical enforcement — a session could invoke `opsx:propose` without ever performing it, silently losing the artifact's traceability] → Mitigate by stating this limitation explicitly in `enrich-us`'s own output next to the "Next action" instruction, consistent with how every other process-only gate in this change (the Blocker/Major severity gate, the verify→review→approval sequence) already states its own non-technical nature rather than implying an enforcement that doesn't exist.
- [Making `enrich-us` mandatory could be perceived as adding friction for trivial or already-detailed work items] → Mitigate via the explicit "preserve meaning and avoid unnecessary expansion when the original task is already sufficiently detailed" rule in the skill's own contract — a well-detailed input should pass through with a short confirmation, not be padded, so the mandatory gate's cost for a good ticket is a quick pass, not a rewrite.
- [A project that manually deletes or edits the SpecBoot-added `.gitignore` block after installation, without deleting the functional rule itself, could still leave `.specboot/staging/` unignored despite the installer having run correctly at install time] → Mitigate by the runtime guard in `enrich-us` itself (Decision above) — it re-verifies at write time, every time, rather than trusting a one-time install-time provisioning to remain true forever.
- [`git check-ignore`'s behavior outside a git repository, or in a repository with a global/user-level gitignore that also covers the path, was not exhaustively tested beyond this correction's own four required scenarios] → Mitigate by treating "not confirmed ignored" as the fail-safe default in every ambiguous case (non-git directory, check command unavailable, or any non-zero/uncertain result) — the guard degrades toward the safer chat-only fallback rather than assuming ignored when uncertain.
- [Documenting the installer/configured-capability distinction does not, by itself, make a fresh adopting repository's Kiro support work — a reader still has to separately configure Kiro if they want it] → Mitigate by cross-referencing `SPECBOOT_ADOPTION_GUIDE.md`'s existing, already-accurate client-selection and adapter-creation sections from the new "Installer Scope" note, rather than leaving the reader with only a "this doesn't work automatically" statement and no path forward.
- [A future reader could still misread a `specboot-verify` PASS on Kiro capabilities in this repository as evidence the installer supports Kiro, if they read the report without the corrected Step 5 wording in mind] → Mitigate by stating the availability-vs-provenance distinction directly in the skill's own Step 5 text (not only in `design.md`), so the caveat travels with every report the skill produces, not just with this change's planning artifacts.
- [The conservative (non-Git) fallback still only recognizes the exact `.specboot/staging/` line, not a broader rule — a Git-less environment with a pre-existing broader `.specboot/` rule will still receive a redundant, appended narrow line] → Accepted, not mitigated further: this is the explicit, requested contract for the fallback path (recognize the exact rule; otherwise append), not an oversight; the redundant line is harmless (still ignored, still not broadened, nothing removed) and Git evaluation — the path that actually detects the broader case — is used whenever it is available, which is the common case for any repository this installer would realistically be run against.
- [`spawnSync('git', ...)` adds a runtime dependency on the `git` binary being on `PATH` for the improved detection to engage at all; an environment with Git installed but not on `PATH` behaves identically to "no Git available" from this function's perspective] → Mitigate by treating any `spawnSync` error (including `ENOENT`) as "evaluation unusable" and falling through to the fallback, rather than throwing or crashing the installer — the installer remains fully functional with or without a reachable `git` binary, only the precision of broader-rule detection changes.
- [Deciding whether a `Question / assumption` row was "actually resolved with recorded evidence" is itself a judgment call a reviewing session makes, not something a mechanical rule can fully police — a session could mark a question resolved without truly having investigated it] → Mitigate by requiring the resolution evidence to be recorded alongside the removal (in the table or the surrounding narrative), so a reader can independently check whether the claimed resolution is actually substantiated, rather than trusting an unexplained disappearance of a row between drafts.
