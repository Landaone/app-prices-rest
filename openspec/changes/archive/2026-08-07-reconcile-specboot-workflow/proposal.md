## Why

SpecBoot's documented OpenSpec workflow (`ai-specs/specboot-instructions.md`) still names commands (`/new`, `/ff`) that do not exist in the OpenSpec 1.7.0 CLI actually installed for this repo's selected clients (Claude, Kiro), and its own distributed template copy (`packages/specboot/template/ai-specs/specboot-instructions.md`) has independently drifted to a *different*, also-stale command list.

OpenSpec 1.7 does ship an official `/opsx:verify` workflow template (confirmed present in the installed package's `dist/core/templates/workflows/verify-change.js`) — an earlier draft of this proposal incorrectly stated 1.7 "dropped" verify entirely. What is actually true: workflow availability is controlled by a `profile`/`workflows` selection that is **global to the machine** (`~/.config/openspec/config.json`), not owned by this repository, and on the reference machine used for this change that global list excludes `verify` (confirmed via `openspec config list`: `profile: custom (explicit)`, `workflows: propose, explore, apply, update, sync, archive (explicit)` — no `verify`). A different developer's machine may have `verify` enabled and would see `/opsx:verify` available.

Regardless of whether `/opsx:verify` is present on a given machine, it does not satisfy this repo's mandatory sequence by itself: read directly, its shipped instructions still route straight to "Ready for archive" after only a Completeness/Correctness/Coherence pass, with no adversarial-review or human-approval concept, and a CRITICAL/WARNING/SUGGESTION taxonomy incompatible with this repo's Blocker/Major/Minor gate. This is the real safety gap this change addresses: the verified historical adoption in `AI4Devs-LTI-extended` (OpenSpec 1.3.1) shipped that same unmodified template, and this repo needs a verification step whose own conclusion respects the mandatory apply → verify → adversarial-review → human-approval → archive sequence, which no version of the official template does on its own.

- **Group 15 (this correction, Major defect):** an independent adversarial review found that `packages/specboot/bin/init.js`'s `.gitignore` staging-rule provisioning contradicted its own promise (proposal.md Group 12 bullet: "if the rule — or an equivalent broader `.specboot/` rule — is already present, make no change"). The implementation only ever checked for the exact trimmed line `.specboot/staging/`; a target repository whose `.gitignore` already contained a broader, equivalent-in-effect rule such as `.specboot/` would still get the narrow rule appended — not incorrect in outcome (still ignored, still no broadening, still no removed content) but a documented no-op guarantee that the code did not actually keep. This group:
  - Changes the detection algorithm to prefer Git's own ignore evaluation (`git check-ignore` against a probe path under `.specboot/staging/`) when running inside a Git repository, so any existing rule — exact, broader, or otherwise — that already causes Git to treat the staging path as ignored is correctly recognized as satisfying the requirement, without writing a custom `.gitignore` pattern parser.
  - Preserves the existing exact-line check as a conservative fallback for environments where Git's evaluation cannot be executed (not a Git repository, `git` unavailable, or the check fails to run cleanly) — behaviorally identical to the pre-Group-15 implementation in that fallback case.
  - Adds isolated tests for the broader-rule no-op case and a broader-rule-with-negation case (documenting Git's real, verified behavior when a rule un-ignores a nested path), alongside re-running the four scenarios already covered by Group 12.
  - Does not change what the installer writes when it does append (the exact same `STAGING_BLOCK`), does not remove/reorder/rewrite existing content, and never writes a bare `.specboot/` rule itself.

- **Group 16 (this correction, Minor defect):** the final independent adversarial review returned `PASS WITH GAPS` with one Minor finding: the deterministic verdict mapping (Group 10, refined through Group 13/14) never explicitly stated how a Findings table containing **only** unresolved `Question / assumption` entries — zero Blocker, zero Major, zero Minor — should be classified. Read literally, such a table could be (mis)routed to the mapping's final "no findings of any severity → PASS" branch, producing a clean PASS while a question still genuinely awaited human or author confirmation. This group:
  - Makes the mapping exhaustive over all four finding categories without adding a fourth severity: `Question / assumption` remains exactly what it always was — a finding category requiring confirmation, not a severity — but the mapping now explicitly states that any unresolved `Question / assumption` (like any Minor) routes to `PASS WITH GAPS`, and that only a Findings table with genuinely nothing left in it (including no unresolved questions) reaches `PASS`.
  - States explicitly that a `Question / assumption` row may be removed from the final Findings table only when it was actually investigated and resolved with recorded evidence during the read-only review itself — never silently dropped, never treated as resolved without that evidence being recorded.
  - Adds four new spec scenarios covering: question-only findings → PASS WITH GAPS; Minor plus question → PASS WITH GAPS; a resolved question with recorded evidence and nothing else outstanding → PASS; no findings at all → PASS.

**BREAKING**: none. The new capability is additive, uses a SpecBoot-owned namespace distinct from `opsx`, existing commands are unchanged, and no OpenSpec-generated client directory or file is modified — only new, separately-namespaced adapter files are added alongside them.

Explicitly out of scope for this change (deferred to later changes): commit/push/PR gate hardening, model-routing policy, full Codex client configuration, broad permission restructuring, onboarding, stack-neutral security auditing, parallel-task orchestration, bulk-archive.
