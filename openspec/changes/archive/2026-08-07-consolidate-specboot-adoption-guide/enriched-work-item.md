## Original

Consolidate `SPECBOOT_ADOPTION_GUIDE.md` into a clean, reusable, stack-neutral adoption procedure.

Context:

The guide currently incorporates a long reference adoption run and many corrective prompt chains. During that run, some requirements were introduced as an original prompt followed by one or more corrective prompts. The guide will be used as the operational source for future SpecBoot adoptions, including a project created with Lovable whose stack must be discovered from repository evidence rather than assumed.

Goal:

Produce a precise work item for updating the guide so a future operator can follow one clean path without replaying historical mistakes or manually combining an original prompt with its later patches.

Required outcome:

- Replace each live "original prompt + corrective prompt(s)" chain with one consolidated reusable prompt containing all verified corrections.
- Keep historical failures, rejected approaches, corrections, and lessons only in clearly labeled historical/troubleshooting/reference sections; they must not appear as sequential steps in the clean execution path.
- Preserve useful evidence from the Java reference adoption, but label it as reference-run evidence rather than a universal result.
- Make the reusable adoption path stack-neutral: discover languages, frameworks, package/build systems, tests, linters, static analysis, shell/OS constraints, and repository conventions from files that actually exist; do not assume Java, Maven, Node.js, frontend/backend architecture, or any particular hosting platform; make technology-specific commands conditional; use only declared/configured project tooling and dependencies; never install or introduce undeclared tooling merely to inspect a repository.
- Make selected-client behavior evidence-driven: distinguish capability availability from installer-provisioning provenance; create adapters only for selected/configured clients; preserve OpenSpec-generated files/directories; validate symlinks, collisions, and client-native invocation names.
- Incorporate the current six-capability daily workflow: `enrich-us` → propose → apply → `specboot-verify` → independent `adversarial-review` → archive.
- Document the gates accurately: `enrich-us` produces `READY FOR PROPOSAL` or `NEEDS CLARIFICATION`; verify PASS only enables adversarial review; adversarial verdict mapping is exhaustive; archive requires both gates plus explicit human approval; commit and push remain separate explicit approvals.
- Consolidate prompts for at least: prerequisite/repository discovery; selected-client and permission configuration; SpecBoot import/initialization; OpenSpec initialization/configuration; CodeGraph configuration when present/applicable; technical-context adaptation; canonical agent inspection/adaptation; canonical skill inspection/adaptation; client adapter planning/creation/validation; `enrich-us`; propose; apply; baseline/testing; SpecBoot verification; independent adversarial review; archive; staged checkpoint and commit/PR preparation.
- Keep permission configuration separate from user-story/OpenSpec requirements: adopters should not need to add command-permission rules to each feature specification.
- Preserve a reusable, repository-shared permission configuration model without machine-specific absolute paths.
- Make examples portable across Bash, zsh, PowerShell, Windows, macOS, and Linux where applicable; avoid presenting one shell's list expansion as universal.
- Do not claim a command ran, a client was discovered, or a capability passed unless actual evidence was recorded.
- Treat unexecuted/failed commands as failures, not inferred passes from empty output.
- Preserve the guide's major 1–22 section structure unless a change is clearly justified; repair anchors, duplicate headings, stale status tables, conflicting counts, and obsolete live command names.
- Avoid a full-file rewrite. Use targeted edits to reduce truncation/corruption risk.
- Do not modify application code, tests, canonical skills, agents, adapters, OpenSpec-generated client files, permissions, or global configuration as part of this guide-only change.
- Do not access the web or external services.
- Do not stage, commit, push, or archive anything.

Evidence sources to inspect: the current `SPECBOOT_ADOPTION_GUIDE.md`; current canonical SpecBoot instructions, standards, skills, and synchronized OpenSpec specification; the archived `reconcile-specboot-workflow` change; repository-local Git history when useful; existing local reference-run documentation only when already readable and relevant.
