## Why

`SPECBOOT_ADOPTION_GUIDE.md` is this repository's operational source for future SpecBoot adoptions, including a project created with Lovable whose stack must be discovered from repository evidence rather than assumed. Two problems currently block that reuse. First, three sections (6, 7, 15) still present a raw historical prompt immediately followed by its corrective/consolidated replacement inline, in the live numbered path — the exact "original prompt + corrective prompt(s)" chain pattern the guide should have already eliminated, and inconsistent with the single-consolidated-prompt pattern Sections 8, 9, 11, and 13 already use. Second, and more materially, the guide's daily workflow content (`Happy Path 2`, Section 18, Section 20's prompt inventory, and Section 21's status table) predates and is completely disconnected from the six-capability workflow (`enrich-us` → propose → apply → `specboot-verify` → independent `adversarial-review` → archive) this repository's canonical `ai-specs/specboot-instructions.md` and synchronized `openspec/specs/specboot-verification-workflow/spec.md` already document — a repository-wide grep of the guide for `enrich-us`, `specboot-verify`, `adversarial-review`, and any `opsx:propose`/`opsx:apply`/`opsx:archive` variant returns zero matches. A handful of smaller, evidence-confirmed gaps compound this: the example Kiro permission YAML in Section 5 is missing the `openspec status` and `git check-ignore` patterns that `specboot-verify` and `enrich-us` now depend on; CodeGraph (Section 4, and the CodeGraph-specific content of Section 5) is presented as an unconditional step in the adoption chain, contradicting this repository's own `.claude/CLAUDE.md` ("skip CodeGraph entirely" when `.codegraph/` is absent) — without making Section 5's separate, mandatory selected-client permission setup appear optional; and the guide has no language distinguishing a client's capability *availability* on disk from the SpecBoot npm installer's actual *provisioning* of it, even though this exact distinction is already canonical (`ai-specs/skills/specboot-verify/SKILL.md` Step 5, `ai-specs/specboot-instructions.md`'s "Installer Scope" note).

## What Changes

- Relocate the three inline historical-prompt-plus-consolidated-prompt chains (Sections 6, 7, 15) so each live section presents exactly one consolidated prompt, matching the pattern already used in Sections 8, 9, 11, and 13. Each relocated historical prompt (preserved byte-for-byte where labeled `HISTORICAL PROMPT — VERIFIED VERBATIM`) and its correction narrative moves into Section 20's existing "Historical prompt chains not recovered verbatim" framework, cross-referenced from the section it came from.
- Author net-new consolidated prompts/procedures for the six workflow capabilities currently absent from the guide — `enrich-us`, propose, apply, `specboot-verify`, independent `adversarial-review`, archive — sourced from and reconciled against `ai-specs/specboot-instructions.md`, the three canonical skill files, and `openspec/specs/specboot-verification-workflow/spec.md`, never re-derived independently.
- Update `Happy Path 2` and Section 18 to name and sequence all six capabilities in order, and state the gate semantics exactly as the canonical spec defines them: `enrich-us` returns `READY FOR PROPOSAL` or `NEEDS CLARIFICATION` and blocks proceeding on the latter; a `specboot-verify` PASS/PASS WITH GAPS makes a change eligible for independent `adversarial-review` only, never archive approval by itself; `adversarial-review`'s verdict mapping is the exhaustive two-phase procedure over Blocker/Major/Minor/unresolved-Question-or-assumption; archive approval requires both gates' PASS/PASS WITH GAPS plus explicit human approval; commit and push remain separate, later, explicit approvals (cross-referencing Section 17's existing "Do not push" / commit-approval boundary rather than rebuilding it).
- Add the missing capability-availability-vs-installer-provisioning-provenance distinction at the point(s) where client selection/adapter creation is discussed (Sections 2, 3, 5, 13), as a short cross-reference to `ai-specs/specboot-instructions.md`'s existing "Installer Scope" section plus a one-line instruction to record actual per-client provisioning provenance in the relevant live validation record(s) — not a duplicated explanation.
- Add the two missing patterns (`openspec status *`, `git check-ignore *`) to Section 5's illustrative Kiro permission YAML code block so the documented example functionally supports `specboot-verify` and `enrich-us` without extra prompting, matching this repository's own `.claude/settings.json`. This edits only the Markdown code block inside `SPECBOOT_ADOPTION_GUIDE.md`; the real `.kiro/settings/permissions.yaml` file is not touched.
- Reframe CodeGraph as an explicit, evidence/decision-gated step: Section 4 becomes skippable in its entirety when CodeGraph is not being adopted for the target repository; only Section 5's CodeGraph-specific content (the `codegraph install` procedure and its client-configuration table/rules/validation) becomes conditional on that same decision, while Section 5's `### Configure Selected-Client Permissions (Early, One-Time)` subsection remains unconditionally mandatory regardless of the CodeGraph decision. `Happy Path 1`'s CodeGraph-specific lines get a conditional marker; its permission-configuration line does not. No section is renumbered.
- Repair any duplicate headings, broken Table of Contents anchors, stale status-table wording, or conflicting counts that the above edits make inconsistent (for example, a CodeGraph row in Section 21's status table needing an "N/A when not selected" qualifier) — a repair-in-place pass scoped to what these edits touch, not an independent full-document audit, since no obsolete command names or broken anchors currently exist (confirmed by grep before this change).
- Add or reinforce a portability note wherever a new or relocated shell example is added, so no single shell's list-expansion behavior is presented as universal, consistent with the guide's own existing Section 22 guidance on this exact failure class.

**BREAKING**: none. This is an edit to a single Markdown adoption guide; no command, skill, agent, adapter, or configuration file's behavior changes.

## Capabilities

None. ### Modified Capabilities

None.
