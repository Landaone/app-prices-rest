## Why

`SPECBOOT_ADOPTION_GUIDE.md` is this repository's operational source for SpecBoot adoptions, and it must be executable end-to-end by a human operator **or** an AI agent. Today it is neither, reliably. The file is 2,045 lines / 87,106 bytes / ~11,786 words in which four documents with different consumption modes and lifecycles are fused together: the reusable procedure (§1–§17 plus §18), per-run evidence capture (20 `Live validation record` fill-in blocks plus §21's `Clean-run status` column), an append-only historical record (§20, plus per-section `Reference outcome` blocks), and support material consulted only on failure (§19, §22, and the closing method/acceptance blocks). A human following the live path top-to-bottom must continuously skip non-executable material; an AI agent must ingest ~22–25k tokens to execute any single step, and cannot generalize step handling because each step has a different shape (`Expected result` + `Common failures` in §1, `Checks` + `Commands` in §10, `Checklist` in §14), no stable step identifier, no resume/state mechanism, and no instruction on what to load.

The mixing is not merely stylistic. The guide's own `Clean-Install Working Method` **already prescribes** five separate companion files (`SPECBOOT_ADOPTION_RUNBOOK.md`, `SPECBOOT_PROMPT_LOG.md`, `SPECBOOT_COMMAND_LOG.md`, `SPECBOOT_DECISION_LOG.md`, `specboot-terminal-session.log`), none of which exist anywhere in this repository's git history — a separation documented as intended but never implemented. And §5 currently holds two steps of **opposite conditionality** — skippable CodeGraph client configuration and unconditionally mandatory selected-client permission setup — a boundary the previous change had to defend with three separate prose warnings ("**never** skipped alongside", "unconditionally mandatory", "not uniformly skippable") because file structure was not enforcing it.

## What Changes

- **Split the guide by consumption mode** into a thin entry file plus a `specboot-adoption/` directory at the repository root: `00-conventions.md` (cross-cutting rules), seven phase files covering current §1–§17, a reduced `08-daily-workflow.md`, `19-permissions-policy.md`, `22-troubleshooting.md`, a `history/` subdirectory (prompt inventory and the Java/Maven reference-run record), and a `run-template/` subdirectory. Grouping is phase-level, not section-level: current sections range 24–185 lines, so one-file-per-section would produce 39-line files beside 185-line ones. Pairing the adapt-then-validate steps the guide already executes together (§9+§10, §11+§12, §13+§14) yields ~14 files of ~25–270 lines.
- **`SPECBOOT_ADOPTION_GUIDE.md` remains at the repository root as the entry point**, keeping its path so no external reference breaks and `git log --follow` continuity is preserved. It carries scope, prompt-label conventions, both Happy Paths, a how-to-use section addressed to humans *and* agents, the step index, and a permanent §-number → file map for back-compatibility.
- **Impose a uniform per-step contract** on every executable step — `Condition` / `Purpose` / `Preconditions` / `Action` / `Approval gate` / `Validation` / `Evidence to record` / `On failure` — replacing today's inconsistent subheadings, and **introduce stable step IDs** (`ADOPT-01` … `ADOPT-17`) decoupled from ordinal position so future insertions never invalidate a cross-reference, a run log, or an agent's resume state. `Action` admits exactly four forms, which is what the steps actually need: shell commands (10 steps); exactly one labeled canonical prompt (6); shell commands that establish or version-gate the prompt's preconditions followed by exactly one labeled canonical prompt (`ADOPT-08`); or a structured written procedure, where the step's work is provisioning and judgement rather than a single command or prompt (`ADOPT-05B`). Never more than one labeled prompt, and never a historical prompt.
- **Add an agent-execution preamble** to the entry file defining the **bounded per-step working set** explicitly as three files: `00-conventions.md`, the single phase file containing the current step, and the operator's filled copy of `ADOPTION-RUN-LOG.template.md`. Loading any of the three is correct behaviour and never a boundary violation. Loading unrelated phase, history, support, or canonical-workflow files remains disallowed unless the current step's documented path requires one. The preamble also states: never self-approve an `[HUMAN APPROVAL REQUIRED]` gate; record evidence after each step; treat an unexecuted or failed command as FAIL.
- **Give the entry file a plain-language human operating model.** All six orientation questions must be answerable from `SPECBOOT_ADOPTION_GUIDE.md` alone, as explanations rather than as pointers to where something is documented: adoption begins at `ADOPT-01` in an existing repository that may have no AI tooling installed; the procedure is sequential, with CodeGraph the only optional branch under the currently preserved methodology (skipping `ADOPT-04`/`ADOPT-05` while mandatory `ADOPT-05B` still follows); planned pause versus unexpected interruption, and how to resume without inferring completion; what evidence *is* and why it is recorded; who may approve what; and what a human does when a step fails, including when the failure is undocumented. Linked files may supply execution detail only after the orientation answer is already clear.
- **Define how the selected client's permission file actually reaches the adopting repository.** The guide requires permission configuration but never says where the file comes from — and `ADOPT-03`'s import deliberately excludes hidden client directories, so nothing else provides it. `ADOPT-05B` becomes the step that explicitly provisions or reconciles it: initialize the client so its project-local structure exists; locate the approved generic baseline; copy it when no target file exists, or merge safely when one does, never overwriting existing project configuration blindly; declare the clients, stacks, shells, and operating systems the project and team support; reconcile the copy against that matrix, removing out-of-matrix permissions while retaining variants every supported environment needs — macOS, Ubuntu/Linux, and Windows where applicable — even when unused on the adopting machine; add only permissions the real project requires; verify no credentials, personal absolute paths, machine-specific dependency locations, or unsafe broad patterns survive; validate client-specific syntax; run fresh-session smoke tests per available client/OS combination, recording unavailable combinations as pending evidence rather than PASS; record baseline source, copy/merge decision, removed and added entries, the support matrix, validation results, and remaining limitations; and leave the approved generic source baseline itself unchanged.
- **Make the import relationship explicit** in `ADOPT-03`: the general SpecBoot copy excludes hidden client directories by design, and `ADOPT-05B` is the mandatory step that provisions or reconciles the selected client's permission file afterward.
- **Guarantee failure-path completeness**: every step's `On failure` must resolve to a recovery that actually applies to that failure, by exactly one of three forms — **(A)** specifically identified applicable recovery instructions **within the same step**, whether expressed as a `Failure`/`Recovery` table or a named inline guidance section; **(B)** a **specifically named entry** in `22-troubleshooting.md`; or **(C)** an **explicitly identified owning step** the operator returns to. A pointer that names no destination, or names one that does not cover the failure, is a defect. Working inline recovery is **not** relocated into `22-troubleshooting.md` merely to make the form uniform — that would duplicate live content and re-create the drift D6 exists to remove. This also adds a dedicated "OpenSpec command not found" entry covering read-only diagnosis of executable resolution, npm global prefix, and `PATH`; explicit return to `ADOPT-02`; renewed human approval before any reinstall or environment mutation; and a full rerun of `ADOPT-08` after recovery — with `ADOPT-08`'s pointer updated to resolve to it.
- **Split §5 into two files** — `02-codegraph.md` (conditional) and `03-client-permissions.md` (mandatory) — so file structure enforces what prose currently enforces by repetition, and **make CodeGraph conditionality machine-decidable** as one decision node with a testable predicate, replacing prose spread across §4, §5, Happy Path 1, and §21.
- **Extract per-run evidence** (20 `Live validation record` blocks, the `Live permission record`, and §21's `Clean-run status` column) into `run-template/ADOPTION-RUN-LOG.template.md` with a step-state checklist for resume; §21's reference-run values move to `history/reference-run-java-maven.md`, keeping the existing caveat that a future run must re-earn PASS rather than inherit it.
- **Reduce §18 to a pointer.** `08-daily-workflow.md` keeps the six-capability sequence, its blocking semantics summary, and the `PENDING END-TO-END VALIDATION` marker, then directs readers to the canonical sources instead of transcribing them. This resolves the drift risk the archived `consolidate-specboot-adoption-guide` change recorded as unsolved and deferred ("if those are edited again afterward, the guide could re-drift"). Verified safe before proposing: `openspec/specs/specboot-verification-workflow/spec.md` (372 lines) already carries the gate semantics densely — `PASS WITH GAPS` ×14, `archive approval` ×8, `Blocker` ×16, `READY FOR PROPOSAL` ×4 — reinforced by `ai-specs/skills/specboot-verify/SKILL.md` and `ai-specs/skills/adversarial-review/SKILL.md`.
- **Repair every reference**: 32 internal anchor links across 25 distinct targets become verified cross-file links, and the four external files that cite the guide by section number are repointed.
- **Preserve all `HISTORICAL PROMPT — VERIFIED VERBATIM` blocks byte-for-byte** through relocation, per §22's own "Prompt labeled verbatim was changed" rule.

**Explicitly not changed**: any adoption procedure, approval boundary, validation criterion, or gate semantic. This is a restructuring, not a methodology revision. Also excluded, by decisions confirmed with the requester before proposal: no `ai-specs/skills/specboot-adopt/` skill and no client symlink work; no addition to `packages/specboot/template/` and no `packages/specboot/package.json` change (the guide is not distributed today and stays undistributed).

**BREAKING**: none. No command, skill, agent, adapter, or configuration file's behavior changes. The entry file's path is preserved, so every existing reference continues to resolve.

## Capabilities

### New Capabilities

None. This change has no spec-level behavior effect on any system — it reorganizes and reshapes documentation describing how to adopt systems (SpecBoot, OpenSpec, CodeGraph) that have their own specs elsewhere. `.openspec.yaml` sets `skip_specs: true` accordingly, matching the precedent of the archived `2026-08-07-consolidate-specboot-adoption-guide` change, which was the same class of work.

### Modified Capabilities

None. `openspec/specs/specboot-verification-workflow/spec.md` is **read as the canonical source** for the §18 pointer reduction and is not modified.

The two `specboot-instructions.md` copies currently differ only at line 204 (image URL) and must be updated in lockstep, preserving that one difference.
- **Not changed**: application source and tests; `ai-specs/agents/*`; `ai-specs/skills/*`; `.claude/`, `.kiro/`, `.cursor/` adapters and symlinks; `openspec/config.yaml`; `openspec/specs/**`; `.gitignore`; `packages/specboot/package.json`; every permission file (`.claude/settings.json`, `.kiro/settings/permissions.yaml`). Each is asserted by a `git diff --exit-code` check in tasks, not by inspection.
- **Not performed**: any live adoption run; staging, committing, pushing, or archiving; web or external-service access.
- **Human-orientation evidence**: the first human-orientation attempt returned a **FAIL** with **all six checks failed**, preserved verbatim as human attempt 1. It was **blocking at the time**, against the pre-D14/D15/D16 entry file, and every one of its six failures was remediated (tasks 8.7–8.10, complete and re-verified). The FAIL is permanent and the transcript is unaltered, but it is **historical defect evidence, not a current release blocker** — the guide version it failed no longer exists. It is recorded as a defect in the guide, not in the reviewer: every answer in the entry file's orientation table was a location rather than an explanation, so a competent reviewer necessarily produced an operating model from general knowledge instead. A second human-orientation attempt after implementation is required, preferring a different reviewer; if the same reviewer is used, prior exposure is recorded as a limitation and the result is not presented as a usability study.
- **Acceptance evidence**: the first fresh-session agent attempt returned a blocking **FAIL** and is preserved as attempt 1 in `reports/agent-acceptance.md`, with tasks 16.1 and 16.6 recorded as FAIL rather than retroactively passed. It exposed the two defects above — the gate working as designed on its first run. A second, genuinely fresh-session attempt after implementation is the only evidence that may satisfy the affected acceptance tasks.
- **Bounded readiness claim.** This change is claimed as **mechanically validated** and **agent-navigability validated against the current post-D4/D13 state**, and therefore **ready for a controlled pilot adoption**. The agent claim was withdrawn when the failure-path and `Action` corrections changed agent-facing prose that attempt 2 never read, and it is **restored only by fresh evidence, never by carrying the old PASS forward**: agent **attempt 3** ran in a genuinely fresh session (human-attested), against the entry file at SHA-256 `0405b6bd…` (18,529 bytes / 287 lines), and returned **PASS** on tasks 16.24–16.26 — all five required demonstrations (form A including `ADOPT-16`'s named inline guidance, form B, form C, `ADOPT-08`'s form-3 `Action`, `ADOPT-05B`'s form-4 `Action`) plus both deciding behaviours: it never read a valid inline or owning-step recovery as undocumented, and it still stopped and escalated where none of the three forms applied. Attempts 1 and 2 stand unaltered as evidence about the states they tested. This is design **D18** applied in both directions — narrow when evidence stops covering the state, restore only when fresh evidence covers it. Two limitations are recorded rather than absorbed: attempt 3 was **scored by the implementing session, not an independent reviewer**, so every scored claim is backed by a mechanical re-derivation against the working tree, and the attempt is **not** an independent review of this change. It is explicitly **not** claimed as validated for independent human usability, and **not** validated end-to-end. Independent human-orientation attempt 2 is recorded as **NOT RUN** — no independent reviewer was available — never as PASS and never as N/A. Human attempt 1 stands permanently as FAIL. The response to an unavailable reviewer is to narrow the claim, not to widen the evidence. **No archive approval is on record, and none may be inferred (design D20).** A `specboot-verify` PASS WITH GAPS, an agent-gate PASS on attempt 3, and D18's sanctioned deferral do not combine into an approval — the first two grant eligibility for the next gate only, and the third governs what may be claimed about the evidence, not what may be done with the change. The human decision to archive with the orientation gate undischarged is **pending**, belongs to a human, and must be recorded explicitly under `reports/` — as an accept or as a defer — before archive. It may never be inferred from a gate verdict, from the absence of open findings, or from elapsed time.
- **Deferred validation contract.** The two unverified properties move to the **first real human-led adoption in another repository**, which must record: the operator's prior exposure to this guide; the full evidence trail; every deviation from the documented procedure; every failure and its recovery; and proposed improvements to the guide and to the troubleshooting file. A **future independent review by an unexposed developer** remains required and is not discharged by the pilot — a pilot operator who has read this guide cannot also be its independent reviewer.
- **Verification**: documentation has no automated test suite, so every acceptance criterion is written to be checkable by a command — a source-section → destination-file mapping table with zero unmapped sections, a link checker, byte-for-byte diffs of verbatim blocks against `git show HEAD:SPECBOOT_ADOPTION_GUIDE.md`, before/after grep counts for invariants (11 approval gates preserved 1:1, record blocks = 20), and two blocking bounded acceptance gates (design D11). The **agent gate** puts a fresh session, given only the entry file, through six behaviours: correct starting step with minimal file loading; the "CodeGraph not adopted" path with selected-client permissions still mandatory; resume from a non-initial `ADOPT-nn` state via the run-log template; stopping at a human-approval gate without self-approving; identifying and recording the required evidence; and classifying an explicitly synthetic failed-or-unexecuted command outcome as FAIL with the documented troubleshooting path followed. The **human orientation and self-description gate** requires a reviewer to answer six entry-level orientation questions from the entry file alone. Both are bounded checks of a restructured document's navigability and self-description: they do not prove a complete real adoption, the human gate does not establish complete human usability or successful human execution, and end-to-end validation will come from the next real SpecBoot adoption performed in another repository. **Verification-evidence persistence contract.** Every `specboot-verify` or `adversarial-review` verdict that informs corrections, accepted gaps, or archive eligibility must be persisted under `reports/` before archive, together with enough provenance to identify the reviewed state: branch, `HEAD`, working-tree scope or fingerprint, client/session evidence, the verdict, and the findings. Persisting a byte-faithful gate record *after* the gate does not invalidate that verdict when only the report record and its task checkbox change. Any change to implementation files, to proposal or design semantics, to acceptance criteria, or to other validated evidence **does** invalidate the affected gate and requires a fresh run. This contract exists so recording a verdict cannot recursively invalidate the verdict being recorded. **Derived figures carry their reproducing command (design D19).** Every block of derived figures in a persisted evidence report states the exact command that reproduces it, runnable from the repository root against the working tree: the figure is a point-in-time snapshot, the command is the durable artifact. This rule exists because five consecutive verification cycles found stale derived figures in the same two reports — VF2/VF3/VF4, re-run 5, VF6–VF9, VF10–VF12, and AR6–AR13 — and every cycle corrected the instances rather than the mechanism, so the next cycle found new ones. No load-bearing figure was wrong in any of those cycles, including the latest: the guide set's invariants were re-derived against the tree and hold. The defect is in the reproducibility of the evidence record. **Strengthened to a literal-command standard after a sixth cycle, found cross-client (AR14).** "States the exact command" turned out to be satisfiable by prose ("link checker", "per-step parse"), by placeholders (`<n>`, `<file>`, `<label>`), by ellipses, and by references standing in for a command ("commands below combined", "the B1/B4/B6 commands"), so the mechanism never actually transferred reproduction to the reader. A `CURRENT` inventory row now satisfies D19 only by carrying the complete literal executable command, or by referencing exactly one stable command ID that resolves one-to-one to a copy-paste executable fenced block in the same report; multi-step checks carry an explicit ordered sequence, every operand is present, and the row's commands must prove **every** figure that row claims. Abbreviation remains legal in the Figures field, never in the Command field. **The invalidation rule is scoped to the *affected* gate, not to every gate.** A correction confined to the evidence reports and to planning artifacts — changing no guide file and no executable contract file — does not reopen the bounded agent gate, because that gate tests what a fresh agent reads and does (`SPECBOOT_ADOPTION_GUIDE.md`, `specboot-adoption/00-conventions.md`, and the phase files), and neither `design.md` nor `proposal.md` is in that set. The boundary is proven, not asserted: SHA-256 over all 15 guide-set files before and after the correction, byte-identical on every one, plus confirmation that no guide path was created or removed.

## Recorded as future changes — not implemented here

Approved separately and deliberately excluded from this change's scope. Recording them keeps
this restructure a restructure; each needs its own proposal, design, and acceptance evidence.

- **Mandatory provider-neutral code-graph capability** — would replace the current
  CodeGraph-specific, optional branch (`ADOPT-04`/`ADOPT-05`) with a required capability
  expressed independently of any one vendor. This change preserves the existing methodology,
  in which CodeGraph remains the only optional branch.
- **Conditional creation of missing client adapters** — adapter creation would detect and
  create what a selected client lacks, rather than assuming the current provisioning split.
- **Pre/post adoption baseline comparison** — the baseline would be captured before adoption
  and compared after, instead of being established only at `ADOPT-16`.
- **Universal checkpoint commit/push policy** — commit and push after each validated
  independent checkpoint, replacing the single end-of-adoption checkpoint at `ADOPT-17` and
  changing this guide's current "STOP before push" boundary.
- **`specboot-adopt` / `specboot-adoption-recorder`** — turning this guide into an invocable
  skill plus an automated evidence recorder, rather than a document set an operator drives by
  hand. Deliberately still out of scope: the document set has not yet passed its human
  orientation gate, and automating an unvalidated procedure would harden its defects.
- **Real project-task E2E validation in a separate branch before creating the adoption PR** —
  would add an end-to-end validation stage the bounded acceptance gates in this change
  explicitly do not provide.
