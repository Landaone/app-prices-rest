## Why

`SPECBOOT_ADOPTION_GUIDE.md` and `specboot-adoption/` define a complete adoption contract addressed to an AI agent, but nothing executes it: adoption today is a human reading a document and pasting canonical prompts, and the guide's own daily-workflow section still carries `PENDING END-TO-END VALIDATION`. Worse, the contract cannot start itself — adoption begins at `ADOPT-01` in a repository that may have no AI tooling at all, yet `ADOPT-03` (`cp -rn <SPECBOOT_SOURCE>/* .`) does not copy hidden client directories, so no AI client can discover the guide or any skill before the step that installs them has already run.

The contract has since moved out of the projects that adopt it: canonical SpecBoot now lives in its own source, supplied to an adoption at run time. That makes copying it into each project the wrong default — a copied guide is a fork the moment the canonical source changes, and a project holding a copy will eventually edit it. Adoption needs to be able to *link* to a canonical source it does not contain, without writing to it and without silently absorbing changes made to it mid-run.

## What Changes

- **New canonical orchestration skill** `ai-specs/skills/specboot-adopt/` — client-neutral and stack-neutral, authored and validated under `ai-specs/skills/writing-skills/` (RED baseline before the skill body exists, then GREEN, then REFACTOR). It executes and resumes the `ADOPT-nn` workflow from a filled run log, stops at every approval gate, and never restates the guide: the guide stays the single authority, the skill is its executor and evidence keeper.
- **Two-layer adoption architecture (design D-Q).** The canonical process is **client-agnostic** — step order, run-log and evidence contract, `PASS` / `FAIL` / `PENDING EVIDENCE` / `NOT SELECTED` semantics, approval gates, the checkpoint/commit/push/bootstrap/de-bootstrap/pilot/improvement rules, the mandatory code-graph capability, and the fresh-session discovery-and-execution evidence contract. Only client-*dependent* actions consult a **per-client recipe**: project-instruction discovery path, skill exposure mechanism, permission-file format and reconciliation, native capability invocation, fresh-session procedure, observable model/reasoning evidence, and client-specific bootstrap/de-bootstrap operations. The human declares the selected client at `ADOPT-00`; the orchestrator then runs the same canonical process against that client's recipe. `NOT SELECTED` is a first-class status: an unselected client has nothing provisioned, nothing validated, and never blocks — unlike `PENDING EVIDENCE`, which asserts intended support a run could not exercise. A `PASS` proves support for the client that produced it and no other.

- **One delivered mode — source-linked — and a canonical source is a precondition, not a branch (design D-R, D-W).** The supplied path must contain `SPECBOOT_ADOPTION_GUIDE.md`, `specboot-adoption/`, and a readable `ai-specs/skills/specboot-adopt/SKILL.md`, checked *before* the first project write and before any orchestration instruction is loaded. Nothing canonical is copied: no guide, no phase files, no skill body, and no `.specboot/bootstrap/` at all. Only project-specific durable state lands under `.specboot/adoption/`, and only the selected client's **temporary** discovery entries are provisioned, pointing at the external canonical guide and skill. The source is read-only for the whole adoption, and its location is **runtime input**: no canonical artifact records a machine-specific path. Where no canonical source is supplied, or the supplied one fails validation, the CLI **fails closed with zero target-repository writes** — it does not route to a second mode.
- **Packaged-snapshot is deferred whole to `add-specboot-packaged-snapshot-delivery` (design D-W).** It is removed from this change's readiness claims, from the entry prompt, from the active requirements, from the documentation, and from the executable user flow, because it is not finishable here: its entry prompt is not distributed with the payload it would be pasted from, it writes before it plans, its client selection is optional (`undeclared` is a reachable committed value), it provisions no client-discovery entry, its manifest records `guide-checksum: null` and `skill-checksum: null`, its resume has never been exercised, and no run has taken it from a virgin repository to a discovered skill. **Its historical evidence is preserved verbatim** — the RED/GREEN records and the behavior-pinning baseline stay as history for a deferred mode rather than being rewritten to match a later scope decision. The named follow-up change must cover entry-prompt distribution, read-only bootstrap planning, explicit client selection, real client discovery entries, non-null payload identity, verified resume, its own answer where symlinks are unavailable, and end-to-end cold-start evidence.
- **Manifest source provenance and drift detection.** `BOOTSTRAP-MANIFEST.json` gains a run-level `source` block recording **portable source identity only**: the `delivery-mode`, the `guide-checksum`, the `skill-checksum`, and the source `git` disposition in one of **three** states, never two — the commit when the source is a **clean** Git working tree; an explicit unavailable record with its reason when the source is not a Git working tree; and, when the source is a Git working tree with **uncommitted changes**, an explicit unavailable record carrying that reason, with the observed HEAD retained as labelled context only and never written to the field a consumer reads as identity, because a HEAD does not identify content the run did not read from it. Never an inferred or invented value in any of the three. **The resolved absolute source path is machine-local runtime state and is never committed**: the block carries an explicit statement that the local source path is resolved per machine and is not stored in the committed manifest, and where a run needs the path afterwards it is kept only in machine-local, git-ignored state under `.specboot/local/` — a convenience pointer holding the path and nothing else, never read as evidence, never an error when absent, and removed by `ADOPT-18`. **Identity is the checksums, and with no path recorded it is the only thing identity can be.** On resume the orchestrator obtains a local source path — from the machine-local store where one exists on this machine, otherwise by asking or rediscovering — and a checksum mismatch is drift that stops the adoption for human reconciliation instead of silently adopting changed instructions; a supplied path is accepted only when the recorded checksums (and the Git commit where one was recorded) match, and no previously used absolute path is ever required to exist.
- **Client selection precedes client-specific configuration (design D-T).** Two routes reach it: the human names the clients, or the orchestrator runs a **read-only** autodiscovery probe, displays the findings, and waits for the human to select. Autodiscovery writes nothing and never authorizes configuration — a discovered client is a candidate, and only an explicitly selected client is provisioned. Everything unselected stays `NOT SELECTED`. **An explicit, supported selection is a precondition of every bootstrap write**: no selection at all refuses, and a selected client with no recipe refuses naming what is supported — both before the first write, both leaving the repository byte-for-byte unchanged, and neither ever recording a placeholder such as `undeclared` into the committed manifest.
- **A short canonical launcher, and one canonical parameterized entry prompt it loads** (design D-V, amended). Starting an adoption no longer means pasting `ADOPTION-ENTRY-PROMPT.md`'s roughly 1,850 words into a fresh chat. It means pasting `specboot-adoption/bootstrap-kit/ADOPTION-LAUNCHER.template.md` — a short, client-neutral template parameterized by exactly one runtime value, `<SPECBOOT_SOURCE>`. The launcher treats that value as a **candidate** source, never as trusted merely because it was supplied, and its entire job is a **read-only** check that four artifacts exist and are readable in it — `SPECBOOT_ADOPTION_GUIDE.md`, `specboot-adoption/`, a readable `ai-specs/skills/specboot-adopt/SKILL.md`, and a readable `specboot-adoption/bootstrap-kit/ADOPTION-ENTRY-PROMPT.md` — **before** loading any orchestration instruction and before any target-repository write. An invalid or absent source stops the launcher with **zero target-repository writes**. A valid source is followed by exactly one further instruction: read `ADOPTION-ENTRY-PROMPT.md` **completely** and follow it exactly. The launcher states, and never itself defines, that no target-repository write is permitted before the approval gate the loaded entry file defines — it never restates the adoption procedure, the client-selection procedure, the checkpoint protocol, or an `ADOPT` step, and the runtime source path it is filled in with lives only in that chat/runtime turn, never in a committed artifact.

  `ADOPTION-ENTRY-PROMPT.md` keeps its existing role and content unchanged: it remains complete in its **parameters and gates** — canonical source path, client-selection route, selected clients, every approval gate, and every fresh-session handoff it will generate — and deliberately silent on **procedure**: it takes its procedure from the `specboot-adopt` skill and names canonical rules by reference rather than restating an `ADOPT` step contract, so the guide stays the only authority. It is no longer the artifact a human pastes — it is **read**, in full, only after the launcher's validation passes — and it embeds no machine-specific path. It is **cold-start correct and executable end to end in source-linked mode**: at the moment the launcher is pasted the target repository has no SpecBoot, no OpenSpec, no `/opsx:*` commands, no discoverable `specboot-adopt` skill, and no `.specboot/` directory, so the whole exchange runs as ordinary prompt text through a seven-step spine an operator can actually perform once the launcher's validation has handed the entry prompt its already-validated source — **(1)** confirm the canonical source the launcher already validated — the guide, the phase directory, and a readable `ai-specs/skills/specboot-adopt/SKILL.md`; **(2)** obtain the procedure by reading that *validated* `SKILL.md` at a source-relative path, a direct read explicitly not native skill discovery; **(3)** obtain an explicit, supported client selection, refusing with zero writes when it is missing or unknown; **(4)** run the complete preflight and present the exact mutation inventory at a human-approval gate; **(5)** provision exactly that inventory, all-or-nothing; **(6)** stop and generate the exact fresh-session handoff prompt; **(7)** attempt native discovery for the first time in that fresh session, resuming from the durable manifest and run log with identity verified by checksum. It asks for a **source**, not for a delivery mode: there is no second mode to choose, and the first artifact an operator's session ever loads is the worst possible place to advertise an unimplemented path. Read-only autodiscovery never authorizes configuration. Native skill discovery is attempted only in that fresh session, which resumes from the durable manifest and run log, verifies source identity by checksum, and blocks on drift. No OpenSpec or `/opsx:*` command is used before `ADOPT-02` has completed and OpenSpec availability has explicitly passed. It makes the operating model explicit: one launcher, one entry prompt it loads, expected human responses at explicit gates, run-generated handoff prompts, deterministic resume from the run log, and **no improvised corrective prompt patches** — an adoption that needed one has found a gap in the launcher or the prompt, which is an improvement proposal rather than normal use. Together the two files are **one governed entry mechanism, not a prompt plus corrective patches**: the launcher never restates what the entry prompt or the guide already define, and the entry prompt's content and scope are otherwise unchanged by this amendment.
- **New portable bootstrap kit** `specboot-adoption/bootstrap-kit/` — a manifest of canonical repository-relative paths (references, never content) plus per-client discovery recipes, reached through the `npx @lidr/lidr-specboot bootstrap` subcommand against a supplied canonical source. Its pack-time payload assembly and drift check are retained as installer machinery for the deferred packaged-snapshot mode and remain covered by their tests; no source-linked run assembles or consumes a payload.
- **Four new adoption steps**, added without renumbering any existing ID: `ADOPT-00` (bootstrap), `ADOPT-18` (de-bootstrap and reconcile client artifacts), `ADOPT-19` (real-project end-to-end pilot gate), and `ADOPT-20` (PR-readiness gate) — the last a step in its own right, not a clause inside the pilot, whose validation checks the recorded PASS evidence for `ADOPT-00`…`ADOPT-19` individually and which is the only step authorized to declare pull-request readiness.
- **BREAKING — the code-graph capability becomes mandatory.** `specboot-adoption/02-codegraph.md`'s "is CodeGraph being adopted?" decision node is replaced by a capability-selection step. The *capability* is required for every adoption; CodeGraph is optional only as the *product* (a company-approved equivalent is equally acceptable). No usable capability is **FAIL** — no waiver, no skip, no `PENDING EVIDENCE`. Adoptions already completed under the previous guide are recorded as pre-amendment, never retroactively failed.
- **BREAKING — push moves inside the contract.** `ADOPT-17`'s "Do not push. Remote mutation is outside this guide entirely." and the matching `00-conventions.md` §Scope boundaries line are amended so each independently validated checkpoint may be committed and pushed to the current working branch under **two distinct approvals**, separated by an evidence-based remote-impact assessment. Unknown or unapproved impact blocks the push. No pull request may be created until the full adoption plus one real-project E2E task pass.
- **Checkpoint model**: a checkpoint is the smallest independently validated `ADOPT` step; grouping dependent steps requires a written justification recorded in a new run-log checkpoint ledger. The checkpoint procedure is defined **once**, as a reusable protocol in `00-conventions.md` — the one contract file already inside every step's bounded working set — and is invoked after each validated step or justified group. `ADOPT-17` keeps its `ADOPT-16 = PASS` precondition and its place as the final checkpoint *of the adoption itself*, and reuses that shared protocol rather than defining its own; its precondition is never repurposed to gate earlier checkpoints. That is not the same as being the last checkpoint of the workflow: `ADOPT-18` commits the updated manifest and `ADOPT-19` is independently validated, so each forms its own checkpoint under the same protocol. The orchestration skill's reference explains how the orchestrator drives the protocol, and does not restate it as a competing authority.
- **Automated installer tests**: the executable changes to `packages/specboot/bin/init.js` and `package.json` gain black-box CLI tests on Node's built-in `node:test`, written to fail before the installer work and pass after it, adding no new dependencies. The suite is **order-independent and passes on its first invocation** — from a clean checkout and from a stale assembled-payload state alike. Any test needing an assembled payload builds it in its own setup; none repairs state on another's behalf.
- **Run-log extensions and a decided location**: `.specboot/adoption/ADOPTION-RUN-LOG.md`, committed, replacing the template's deliberately undecided "your team's choice" paragraph — AI-driven resume needs a deterministic path. New blocks cover the checkpoint ledger, improvement proposals, client/company adaptations, and code-graph capability selection.
- **Bootstrap landing zone**: `.specboot/adoption/` holds the durable, committed `BOOTSTRAP-MANIFEST.json` and run log; `.specboot/bootstrap/` (transient, git-ignored payload) belongs to the deferred packaged-snapshot mode and **is never created by a source-linked run**. Its ignore rule is still provisioned unconditionally, as a mode-independent property of the installer rather than a claim that the mode is available. `ADOPT-18` therefore removes only the project-local temporary discovery entries and the machine-local source-path store — leaving the external canonical source untouched — and records the payload and container obligations as `SKIPPED — source-linked mode` rather than as passed or silently omitted. Source-linked discovery entries name an absolute external path, so they are machine-local: they are excluded from every checkpoint's staged scope, are never committed, and are removed or byte-restored by `ADOPT-18`.
- **A complete preflight precedes every write, and provisioning is all-or-nothing (design D-X).** Before the first target-repository write the run resolves every path the selected client's recipe and the durable state will occupy, classifies each as absent, pre-existing-untouched, or colliding, and reports **all** collisions at once — not one per failed write. The human-approval gate then presents the exact mutation inventory: each path, what will be created or modified, by what mechanism, and whether it is reversible; the run performs exactly that and nothing else. A provisioning failure restores the pre-provisioning state, leaving no orphaned discovery entry, manifest, run log, ignore rule, or machine-local store.
- **Where the selected client cannot natively discover the external skill without symlinks, the run fails closed (design D-D).** Discovery is a property of the client, not of the filesystem: a plain pointer file naming an external path is not a discovered skill and is never recorded as one. The run stops before provisioning and reports the capability limitation — which client, which mechanism, what was attempted — rather than provisioning a degraded entry and letting the fresh-session probe discover the truth later. A content copy as a fallback remains forbidden outright.
- **`sync-agent-symlinks` coverage** moves from a hardcoded `.claude` + `.cursor` list to the repository's selected clients — `.kiro/` exists here and is unmanaged by it today, while `.cursor/` does not exist at all.
- **Improvement proposals after every validated checkpoint**, recorded with a status and never applied silently; guide edits continue to go through the normal OpenSpec change workflow. Findings are recorded in the **project's** run log, and the project never edits a guide, phase file, or troubleshooting entry — in source-linked mode it holds no copy to edit at all, which is what makes the rule enforceable rather than merely stated. Accepted improvements are applied later, in **one governed batch, to the canonical SpecBoot source** (design D-U), and are never consumed by the run that raised them.
- **The template gains the two missing daily-workflow skills, and `ADOPT-18` gains a completeness precondition (design D-Y).** A completed pilot run against this branch's committed guide (`9f08281`) reached `ADOPT-19` `BLOCKED`: `specboot-verify` and `adversarial-review`, two of the six workflow capabilities `ai-specs/specboot-instructions.md` declares mandatory, do not exist anywhere in `packages/specboot/template/ai-specs/skills/` — a template defect, not something specific to the pilot's target repository, that would identically block this change's own still-unexecuted Group 21 pilot (task `21.7`) the moment it runs. Both skills are added to the template, imported by `ADOPT-03` like `enrich-us`; `ADOPT-11`/`ADOPT-12` gain a completeness check against the six-capability list, distinct from their existing stack-adaptation check; and that completeness check becomes an additional precondition of `ADOPT-18`, which currently removes the only project-local pointer that could otherwise self-repair the gap in-repo. The same evidence narrows `ADOPT-18`'s existing unconditional second fresh-session `ADOPT-15` re-run to only when de-bootstrap touched something beyond the manifest's exact `bootstrap-created` entries — the guide's single most expensive step, priced twice per adoption today for a check that, in the ordinary case, `ADOPT-14`'s cheap filesystem re-check already covers.
- **`ADOPT-02`, `ADOPT-05`, and `ADOPT-13` gain the conditional treatment the tenth revision's own reasoning named but never wired in, and two more automatic behaviors close the remaining gaps (design D-Z, parts 6-8).** `ADOPT-02` skips its install/upgrade command and gate entirely when the installed OpenSpec version already meets the documented requirement; `ADOPT-05` auto-approves when the operator's choices match the step's own documented least-privilege defaults; `ADOPT-13` auto-approves when the exposure plan is exactly what `ADOPT-09`–`ADOPT-12` already validated. `ADOPTION-LAUNCHER.template.md` gains a mechanical fail-closed check — before its existing four-artifact validation — for a target repository that turns out to be the canonical source's own working directory. **Corrected in the twelfth revision**: the check compares filesystem location only, never Git identity (common directory, root commit, origin) — a real fresh-session run against this project's own worktree-based topology showed the original wording false-positived on every legitimate pairing, since every `app-prices-rest-specboot-*` worktree and the canonical source share the same underlying repository by design. `09-bootstrap.md`'s fresh-session handoff (and `ADOPT-18`'s equivalent) is reworded so an executing run cannot read it as a live "continue or hand off?" choice, closing friction the pilot recorded even though the guide's prior wording already stated the handoff as an instruction.
- **Human approval becomes mechanical wherever a deterministic check already exists (design D-Z).** The same pilot recorded ~39 checkpoint-related questions in one run; ~27 were pure commit/push/inventory ceremony on already-validated, unchanged content. `Allowed modifications` becomes a ninth field of the step contract in `00-conventions.md`, authored by the guide maintainer in advance (a closed exact-path list for deterministic steps, a closed rule for conditional ones) rather than derived live by the executing run; a new `ADOPTION-AUTHORIZATION.md` — one file per adoption run, never one per step, **created by `ADOPT-00` itself and filled progressively as `ADOPT-02`/`ADOPT-05`/`ADOPT-05B` are reached (design D-Z, part 2a, thirteenth revision — the tenth revision defined the file but never wired its creation to any step, a gap the live pilot's first real run exposed)** — records what the human granted (client selection, the declared team environment matrix, the standing commit-and-push authorization); and the checkpoint protocol's two approval gates auto-approve only when the staged set is a subset of the step's declared allowlist **and** a standing authorization covers it, logging evidence instead of asking — any path outside the allowlist is `FAIL_CLOSED`, not a question. The same mechanical-evidence principle closes `ADOPT-06`'s content gate via a citation-check (every claim, including narrative "Known Risks" content, must resolve to a code citation via the selected code-graph capability) without weakening `ADOPT-06`'s existing rule that it documents known code defects and never resolves them. `ADOPT-07`/`ADOPT-08` and `ADOPT-13`/`ADOPT-14` are additionally grouped under the existing `D-F` checkpoint-grouping rule, correcting an inconsistency where `ADOPT-09`/`ADOPT-10` and `ADOPT-11`/`ADOPT-12` already receive that treatment and these structurally identical pairs did not.
